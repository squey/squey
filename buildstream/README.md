
# Development

## Clone the project

Note : you should have `git` and `git-lfs` installed.

```
git clone --recursive https://gitlab.com/squey/squey.git
```

## Quick start: the devcontainer

The fastest way to build Squey is a prebuilt container image holding the whole
build sysroot. It requires nothing on the host but a container engine, and it
skips BuildStream entirely. Budget around 12 GB of disk for the image, plus the
build directory.

Open the repository in an editor that supports the
[Development Containers specification](https://containers.dev) -- VS Code with
the [Dev Containers](https://marketplace.visualstudio.com/items?itemName=ms-vscode-remote.remote-containers)
extension, GitHub Codespaces, JetBrains Gateway -- and accept the "Reopen in
Container" prompt. Then, from a terminal inside the container:

```
.devcontainer/configure_builds.sh
cmake --build builds/x86_64-linux-gnu/Clang/RelWithDebInfo
```

Or without an editor, through the [devcontainer CLI](https://github.com/devcontainers/cli):

```
devcontainer up --workspace-folder .
devcontainer exec --workspace-folder . .devcontainer/configure_builds.sh
devcontainer exec --workspace-folder . cmake --build builds/x86_64-linux-gnu/Clang/RelWithDebInfo
```

`configure_builds.sh` is also declared as the `postCreateCommand`, so an editor
may well have run it for you already; running it again costs nothing, as it
leaves an already configured directory alone. The CLI, as of 0.89.0 against
podman, does not run it -- hence the explicit call above.

**Podman or Docker.** `devcontainer.json` carries `--userns=keep-id`, which
podman needs and Docker does not have. Under rootless podman the container user
otherwise lands on a subordinate uid of the host, owning nothing: it cannot even
write into the workspace, and cannot reach the compositor socket. Under Docker
that uid is already the host one, so **delete that `runArgs` line**, which
Docker would reject.

**What it does not do.** Only a native Linux build. Cross-compilation to Windows
and macOS, the flatpak, MSIX and DMG packaging and everything the release
pipeline does stay in BuildStream: use the development shell below for those.

**If the image will not pull.** A branch pins the image of its own dependency
graph, and that image is published by the merge request pipeline. On a branch
that never had one -- an old commit, or a graph nobody has proposed yet -- the
pull fails with `manifest unknown`. Open the merge request and let the CI
publish it, or build it locally with the command under "Publishing the image".

### Running the GUI

The container talks to the host compositor directly: `devcontainer.json` binds
the Wayland socket in, so a build started here puts its window on the desktop
like any other application. No waypipe -- that exists in the development shell
below because the BuildStream sandbox cannot see the host socket and has to
tunnel it over ssh; a container shares the kernel and just mounts it.

```
buildstream/files/flatpak/run_cmd.sh \
  builds/x86_64-linux-gnu/Clang/RelWithDebInfo/squey.sh
```

`squey.sh` is generated by cmake into the build directory and points the plugin
paths at it; `run_cmd.sh` is the same wrapper the packaged application uses, and
sets up the OpenCL vendor files. Pass `debug` to `squey.sh` to start under gdb.

Settings, recent sources and lists live on a volume, and the temporary files
directory Squey asks for on a first start is shipped writable in the image, so
neither the greeting dialog nor the configuration comes back every time the
container is recreated.

Rendering falls back to the CPU out of the box: the PortableCL of the sysroot is
built without ICD support, so the container has no OpenCL platform of its own,
which is what the `FORCE_CPU` of `devcontainer.json` accounts for. To render on
the GPU instead, merge the output of

```
buildstream/scripts/devcontainer_gpu_args.sh
```

into `devcontainer.json` and drop `FORCE_CPU`. It cannot be committed once and
for all: the flatpak runtime carrying the NVIDIA userspace is named after the
driver version, so it differs per machine.

One trap is worth knowing, as it costs a crash rather than a fallback. Once the
GPU is visible, Squey finds the device, reports it, and then dies on
`CL_BUILD_PROGRAM_FAILURE` (-11) while building its kernels, unless the runtime
directory is on `LD_LIBRARY_PATH`: `run_cmd.sh` links `libnvidia-ptxjitcompiler`
into the ICD directory, but the OpenCL compiler dlopens `libnvidia-nvvm.so.4`
too, and nothing points at it. The generated fragment sets the path.

### Publishing the image

The image tag is a digest of the dependency graph, computed from the cache keys
BuildStream already assigns to every build dependency of `squey.bst`. It is
invariant to anything under `src/`, so only a commit that changes the
dependencies calls for a new image -- around thirty a year, against several
hundred commits. `.devcontainer/devcontainer.json` pins the reference the same
way `.gitlab-ci.yml` pins `BASE_IMAGE_NAME`, and the pin travels with the branch.

Publishing is never a manual step. The `ensure devcontainer image` job runs on
every merge request and refuses to go green unless the pin matches the
dependency graph *and* names an image the registry really holds -- publishing
it itself when it does not. A merge request can therefore only be merged once
its image exists, so the default branch never points at something nobody can
pull.

The job is not narrowed to the paths the tag is derived from. It could be, and
would be correct for exactly as long as that list and those paths agreed; it
would also stand by while an image disappeared from a repository that had not
changed. Running every time costs a `bst show` and a registry query, seconds
against the pipeline it sits in, and never rebuilds an image that already
exists. It runs on the default branch for the same reason.

To publish by hand -- when working offline, or on a target the CI does not
cover:

```
buildstream/scripts/devcontainer_image_tag.sh                        # tag of the current graph
buildstream/scripts/build_devcontainer_image.sh --push=true --update-pin=true
```

Note that the staged sysroot is around 11 GB, so point `TMPDIR` at a disk with
room to spare if `/tmp` is a tmpfs.

## Development shell

The BuildStream sandbox: slower to enter than the devcontainer above, and the
only way to cross-compile and to produce a package.

Note : you should have `python` installed.

```
cd squey/buildstream && ./dev_shell.sh
```

From then you can choose to use the development shell to compile and run the software as such:

```
cd builds/{x86_64-linux-gnu,x86_64-apple-darwin,aarch64-apple-darwin}/{Clang,GCC}/{Debug,RelWithDebInfo} && cmake --build . [ && ./squey.sh ]
```

or you can continue to configure an IDE.

## Configure Visual Studio Code

Install the following extensions :

1. [C/C++ Extension Pack](https://marketplace.visualstudio.com/items?itemName=ms-vscode.cpptools-extension-pack)
2. [CMake](https://marketplace.visualstudio.com/items?itemName=twxs.cmake)
3. [Remote Development](https://marketplace.visualstudio.com/items?itemName=ms-vscode-remote.vscode-remote-extensionpack)
4. [CodeLLDB](https://marketplace.visualstudio.com/items?itemName=vadimcn.vscode-lldb)

The `dev_shell.sh` script is embedding a local SSH server as well as a [waypipe](https://gitlab.freedesktop.org/mstoeckl/waypipe) tunnel that permit to debug the GUI application inside BuildStream development sandbox under Wayland. So don't forget to have it running to be able to open the project in vscode :

```
cd squey/buildstream && ./dev_shell.sh
```

Just append the [preconfigured SSH host configuration](sshd/ssh_config.squey) to your local SSH configuration file:

```
cat buildstream/sshd/ssh_config.squey | tee -a ~/.ssh/config
```

Then use the vscode `Remote Explorer` extension to connect to the `SqueyLinux` hostname using a ssh key (note: password login is not supported).

Each target platform uses its own port, so sandboxes for several targets can run at the same time: connect to `SqueyLinux` for a native Linux sandbox (port 6666), `SqueyWin` when it was started with `--target_triple=x86_64-w64-mingw32` (port 6667), and `SqueyMac` for an `*-apple-darwin` one (port 6668).

# Flatpak

## Generating and installing a local flatpak package

```
cd buildstream && ./build.sh --flatpak-export=true --flatpak-repo=local_repo
```

Adding the flatpak local remote (once):
```
flatpak --user remote-add --no-gpg-verify squey_local ./local_repo
```

Installing a local package:
```
flatpak install --user squey_local org.squey.Squey//main
```
